===== POTENTIAL CERTIFICATION ERRORS =====  
  
RE: Requirement RP 2.1 / RP 4.1 — getUserData API  
NightscoutTV for Roku respectfully requests an exemption from the getUserData requirement on the following grounds:  
• NightscoutTV does not implement user account creation, user registration, or email-based authentication of any kind:   
  The "Access Token" field flagged during certification is not a user credential — it is a server-side API access token generated by, and specific to, the user's own hosted Nightscout server instance.  
• The term "Access Token" is not our terminology — it is the exact term used by the Nightscout Project's own Admin GUI (Nightscout > Admin Tools > Subjects).   
  We really need to match it precisely, to clearly guide users.  
• The token is not an email address, password, or PIN code. It is an alphanumeric string (e.g. read-abcdef1234567890) that grants read access to the user's personal data server that hosts their own Continuous Glucose Monitor (CGM) health info. It is analogous to an API key, and NOT a login credential.  
• There is no NightscoutTV account, no NightscoutTV user database, no email address collected, and no registration flow.   
  The getUserData API would return information that this app has no use for and would never store, transmit, or act upon.  
• NightscoutTV is a free, open-source, non-commercial display utility for the DIY Diabetes community.    
  Its sole function is to display CGM data from the user's own server on their Roku device.  
  
We respectfully submit that Requirement RP 2.1 / RP 4.1 was designed for channels implementing traditional account-based authentication, and does not apply to this use case.

===== CERTIFICATION ERRORS =====  
  
RE: Requirement 4.5 — In-Channel Screensaver / Interactive Functionality  
NightscoutTV requests a policy exception on the following grounds:  
• NightscoutTV is a native Roku screensaver channel implementing the standard screensaver API (RunScreenSaver, RunScreenSaverSettings) exactly as documented. 
  - It also supports RunUserInterface for Home screen launch, which is the specific behavior we are requesting an exception for.  
• When running in screensaver context, NightscoutTV is fully NON-interactive:  
  
Key Points:   
• onKeyEvent() explicitly returns false for all keypresses, passing control back to the Roku OS  
• All interactive UI elements (hour selection buttons, footer instructions) are hidden or rendered nearly invisible  
• No user input affects screensaver behavior in any way — the OS dismisses it normally on any keypress  
  
Why?   
• The dual RunUserInterface / RunScreenSaver architecture is a deliberate design choice to serve the diabetes DIY community, who benefit from being able to launch the display manually as well as have it run as a screensaver. 
  - No interactive functionality crosses between the two contexts into screensaver operation.  
• Source code is publicly available and auditable at: https://github.com/ChaseCarHG/NightscoutTV   
We respectfully request that Requirement 4.5 be waived given the above.
